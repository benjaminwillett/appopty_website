What we report on

Everything between the user and the server.

Choose the areas you run. Each section records its scope, its collection date and any gaps in the evidence.

  • Application delivery controllers

    Controllers such as NetScaler and F5: virtual servers, policies, pools and the servers behind them.

  • Load balancers

    Load balancing methods, persistence, health checks and how many servers are up in each pool.

  • Remote access gateways

    Gateways, sign-in factors, session settings and the resources each gateway publishes.

  • Reverse proxies

    Which names and paths are published, where each one is forwarded and what is rewritten on the way.

  • Web application firewalls

    Which applications have a profile, whether it blocks or only logs, and which have none.

  • Cloud application gateways

    Listeners, routing rules, back-end pools and firewall settings on gateways in your cloud accounts.

  • Kubernetes ingress controllers

    Ingress hosts and paths, the services behind them and whether each is published with TLS.

  • Application dependency mapping

    Each application traced from its name to its servers, with the components it shares with others.

  • Audit evidence and coverage

    Included with every report: the scope read on each platform, the date it was collected and anything that could not be read.

How it works

From controller configuration to application reports.

Three steps take you from agreed scope to a report for every application.

  1. 1

    Connect

    Agree the controllers, gateways and clusters in scope, then grant read-only access to each one.

  2. 2

    Trace

    Follow each application from its address to its servers. Note the scope, collection date and evidence gaps.

  3. 3

    Review and refresh

    Give engineers the findings in priority order. Repeat the collection to show what changed.

What access we need

Read-only access to each platform in scope. Nothing is created, changed or deleted.

  • Application delivery controllers

    A read-only account on each controller in scope, such as NetScaler and F5.

  • Cloud application gateways

    A read-only role on each cloud account in scope.

  • Kubernetes

    Read-only access to the ingress resources in each cluster in scope.

  • An application list, if you have one

    Names and owners, so the reports use the names your teams know.

Findings and evidence

More than configuration. Findings for each application.

Each finding names the application it affects, the evidence it rests on and the next step.

  • For engineers: a prioritised list

    Findings in priority order, each traced to the virtual server, policy or certificate it comes from.

  • For application owners: one sheet each

    A page per application: how it is published, what it runs on and what it depends on.

  • Between refreshes: what changed

    Repeat the collection to show what was added, removed or reconfigured since the last report.

The finding above is illustrative and uses the fictional Riverside Technology Group estate. Findings are based on what was read from each platform at the time of collection, and should be reviewed by your engineers before any change is made.

Questions about Appopty

What does Appopty report on?

Application delivery controllers, load balancers, remote access gateways, reverse proxies, web application firewalls, cloud application gateways and Kubernetes ingress controllers, with application dependency mapping across them.

Which platforms are covered?

Application delivery controllers such as NetScaler and F5. Tell us what you run and we will confirm what each section can cover.

What access is needed?

Read-only access to each platform in scope. See what access we need.

Does collection change anything?

No. Collection reads configuration and state through read-only access. It does not create, change or delete anything.

Are the reports available now?

Reporting capabilities are in development. The report previews on this page are illustrative layouts that use synthetic data for a fictional organisation.
